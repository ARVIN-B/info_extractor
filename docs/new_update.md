4. قبل از ایجاد هر کلاس، تابع، مدل، سرویس یا connector جدید، بررسی کن آیا مشابه آن از قبل وجود دارد یا خیر.
5. از ایجاد منابع تکراری، آداپترهای تکراری و اجرای چندباره یک درخواست یکسان جلوگیری کن.

7. وابستگی جدید فقط در صورت نیاز واقعی اضافه شود.
8. نسخه پکیج‌های MCP باید مشخص و قابل بازتولید باشد.
9. هیچ API، ابزار، endpoint، قابلیت یا رفتار یک MCP را بدون بررسی واقعی کد و schema آن فرض نکن.
10. اگر یک MCP در دسترس نیست یا ساختار آن با انتظار پروژه تفاوت دارد، آن را به‌صورت شفاف مدیریت کن؛ نه اینکه داده جعلی تولید کنی.
11. از تغییرات مخرب دیتابیس و حذف اطلاعات قبلی جلوگیری کن.
12. Migrationها باید backward-compatible و قابل اجرا روی دیتابیس موجود باشند.
13. هیچ API Key، رمز عبور، Secret یا اطلاعات حساس را در کد یا Git قرار نده.
14. اطلاعات تماس خصوصی اشخاص را استخراج نکن؛ فقط اطلاعات عمومی مربوط به کسب‌وکارها و راه‌های تماس تجاری منتشرشده را ذخیره کن.
15. محدودیت‌های سایت‌ها، robots policy، شرایط استفاده و محدودیت‌های دسترسی را رعایت کن. از دور زدن CAPTCHA، احراز هویت یا محدودیت‌های امنیتی استفاده نکن.

# بخش پنجم: سیستم هوشمند Fallback

این مهم‌ترین بخش ارتقا است.

سیستم باید در صورت محدودیت یک منبع، بتواند از منابع جایگزین استفاده کند و کار Job را تا جای ممکن ادامه دهد.

## 5.1. تشخیص نوع خطا

خطاها باید به دسته‌های مشخص تقسیم شوند:

- RATE_LIMIT
- DAILY_QUOTA_EXCEEDED
- LONG_COOLDOWN
- FAIR_SHARE_EXHAUSTED
- GLOBAL_CALL_BUDGET_EXHAUSTED
- SOURCE_TIMEOUT
- SOURCE_UNAVAILABLE
- CONNECTION_ERROR
- TOOL_SCHEMA_ERROR
- AUTHENTICATION_ERROR
- INVALID_ARGUMENTS
- EMPTY_RESULT
- INTERNAL_ERROR

این دسته‌بندی باید ساختاریافته باشد، نه صرفاً بر اساس مقایسه رشته‌های خطا.

تا حد ممکن اطلاعات زیر را از Exception و پاسخ MCP استخراج کن:

- HTTP status code
- Retry-After
- reset timestamp
- محدودیت زمانی اعلام‌شده
- متن اصلی خطا
- ابزار ایجادکننده خطا
- source مربوطه

## 5.2. Fallback بین منابع مشابه

برای هر گروه، منابع جایگزین تعریف کن.

مثال:

**کشف کسب‌وکار محلی**

Neshan → Balad

Balad → Neshan

**فروشگاه اینترنتی**

Emalls → Torob → Digikala → SnappShop

**فروشندگان بازارگاه**

Basalam → منابع بازارگاهی معتبر دیگر

**شرکت‌های استخدام‌کننده**

Jobinja → Jobvision → IranTalent → e-Estekhdam

**شرکت‌های ثبت‌شده**

Rasmio → سایر منابع عمومی معتبر اطلاعات شرکت

این زنجیره‌ها فقط پیشنهاد اولیه هستند. ترتیب نهایی باید با توجه به نوع داده، کیفیت، پوشش جغرافیایی و قابلیت واقعی منابع تنظیم شود.

### قوانین Fallback

1. اگر منبعی به 429 خورد، درخواست‌های بیشتر به همان منبع را بی‌دلیل ادامه نده.
2. نتیجه‌هایی که قبل از خطا گرفته شده‌اند باید حفظ شوند.
3. ابتدا منبع جایگزین مرتبط را امتحان کن.
4. داده‌های حاصل از منبع جایگزین باید وارد همان Pipeline استاندارد شوند.
5. شناسه منبع، provenance و Evidence باید حفظ شوند.
6. اگر منبع جایگزین هم محدود شد، به منبع بعدی برو.
7. یک منبع نامرتبط را صرفاً برای ادامه دادن درخواست‌ها انتخاب نکن.
8. اگر هیچ منبع جایگزینی باقی نمانده، سیاست انتظار و ادامه را اجرا کن.
9. Fallback نباید باعث اجرای دوباره جست‌وجوهای موفق قبلی شود.
10. هر منبع در یک Job فقط به تعداد مشخص و کنترل‌شده Retry شود.

**نکته مهم:** Fallback به معنی تغییر منبع است، نه تغییر هویت کسب‌وکار یا ادغام بی‌دلیل نتایج مشابه.

# بخش ششم: مدیریت حرفه‌ای Rate Limit و Retry

## 6.1. تفاوت دو نوع محدودیت

دو وضعیت کاملاً متفاوت داریم:

### وضعیت اول: محدودیت داخلی پروژه

مثال:

`basalam reached its fair share of the job call budget; remaining calls are reserved for other selected sources.`

این خطا HTTP 429 نیست.

معنی آن این است که منبع سهم مجاز خودش را مصرف کرده و باید فرصت اجرای سایر منابع حفظ شود.

در این حالت:

- خطا ایجاد نکن.
- منبع را به‌عنوان FAILED علامت‌گذاری نکن.
- درخواست اضافه به آن منبع ارسال نکن.
- وضعیت آن را به‌صورت BUDGET_EXHAUSTED یا TRUNCATED ثبت کن.
- اجرای منبع بعدی را ادامه بده.
- نتیجه‌های قبلی را نگه دار.

وقتی بودجه یک منبع تمام شده، نباید بودجه رزروشده سایر منابع را مصرف کند.

### وضعیت دوم: محدودیت واقعی سرویس خارجی

مثال:

- HTTP 429
- Too Many Requests
- Retry-After
- Rate limit exceeded
- Daily quota exceeded
- Monthly quota exceeded

در این حالت باید سیستم Retry و Fallback اجرا کند.

## 6.2. تشخیص مدت محدودیت

مدت انتظار را با اولویت از اطلاعات واقعی سرویس تشخیص بده:

1. Retry-After برحسب ثانیه
2. Retry-After به‌شکل HTTP date
3. reset timestamp
4. پیام خطا
5. مقدار پیش‌فرض تنظیمات

زمان‌ها باید به‌درستی به ثانیه تبدیل شوند.

از محدود کردن مصنوعی زمان اعلام‌شده به یک ساعت خودداری کن؛ این کار می‌تواند باعث شود یک محدودیت چندساعته اشتباهاً به‌عنوان محدودیت یک‌ساعته تفسیر شود.

## 6.3. سیاست انتظار

سیاست زیر را پیاده‌سازی کن:

### محدودیت کوتاه

اگر زمان اعلام‌شده کمتر از یک ساعت باشد:

- ابتدا Fallback را بررسی کن.
- اگر منبع جایگزین مناسب موجود است، کار را با آن ادامه بده.
- اگر منبع جایگزین وجود ندارد، امکان انتظار و Retry کنترل‌شده را بررسی کن.

برای محدودیت‌های کوتاه، از Backoff و Jitter استفاده کن.

مقادیر قابل تنظیم در `.env` باشند، برای مثال:

- `SOURCE_RATE_LIMIT_MAX_INLINE_WAIT_SECONDS`
- `SOURCE_RATE_LIMIT_DEFAULT_COOLDOWN_SECONDS`
- `SOURCE_RATE_LIMIT_MAX_RETRIES`
- `SOURCE_RATE_LIMIT_BACKOFF_MULTIPLIER`
- `SOURCE_RATE_LIMIT_JITTER`
- `SOURCE_RATE_LIMIT_LONG_THRESHOLD_SECONDS`

مدت انتظار نباید باعث عبور از Celery task time limit شود.

اگر انتظار طولانی‌تر از محدوده مجاز اجرای داخل Task است، به‌جای Sleep طولانی، Job را با وضعیت مناسب ذخیره و ادامه آن را از طریق Celery countdown زمان‌بندی کن.

### محدودیت یک ساعت یا بیشتر

اگر سرویس صراحتاً محدودیتی برابر یا بیشتر از یک ساعت اعلام کرد:

- روی همان منبع منتظر نمان.
- Retry مجدد به همان منبع انجام نده.
- cooldown را به‌صورت ماندگار ذخیره کن.
- اگر منبع جایگزین وجود دارد، از آن استفاده کن.
- اگر جایگزینی وجود ندارد، ادامه همان بخش را متوقف کن.
- Job اصلی را به‌دلیل این محدودیت FAILED نکن.

اگر محدودیت روزانه یا ماهانه اعلام شد، آن را در دسته LONG_COOLDOWN یا QUOTA_EXCEEDED قرار بده و تا پایان محدودیت، درخواست مجدد نفرست.

**هیچ‌وقت محدودیت یک‌ساعته یا چندساعته را با Retryهای مکرر نادیده نگیر.**

## 6.4. Cooldown مشترک

محدودیت منبع باید بین تمام Jobها و Workerها مشترک باشد.

اگر Neshan در یک Job محدود شد، Job دیگری نباید بلافاصله همان درخواست را به Neshan ارسال کند.

از Redis برای هماهنگی سریع و از دیتابیس موجود برای ماندگاری وضعیت استفاده کن.

در صورت وجود cooldown فعال:

- منبع را موقتاً Skip کن.
- اطلاعات cooldown را ثبت کن.
- از Fallback استفاده کن.
- اگر cooldown تمام شد، امکان استفاده مجدد فراهم شود.

## 6.5. جلوگیری از Retry غیرضروری

این موارد نباید باعث Retry بی‌دلیل شوند:

- Empty Result
- Invalid Arguments
- Tool Not Found
- Schema Validation Error
- Fair Share Exhausted
- Global Budget Exhausted

برای هر دسته سیاست Retry مشخص داشته باش.

# بخش هفتم: اصلاح تقسیم بودجه بین منابع

سیستم فعلی دارای این تنظیمات است:

- `SOURCE_MAX_CALLS_PER_JOB`
- `MAX_MCP_CALLS_PER_JOB`

الزامات:

1. برای منابع انتخاب‌شده سهم اولیه رزرو شود.
2. یک منبع نتواند کل بودجه را مصرف کند.
3. اگر یک منبع زودتر از حد انتظار تمام شد، ظرفیت بلااستفاده آن در صورت امکان بین منابع دیگر توزیع شود.
4. محدودیت fair-share نباید به‌عنوان خطای خارجی یا باگ ثبت شود.
5. تعداد درخواست‌های Fallback نیز در بودجه کلی حساب شود.
6. برای جلوگیری از رقابت Workerها، شمارنده‌ها باید اتمیک یا به‌شکل امن مدیریت شوند.
7. اجرای مجدد Job نباید باعث مصرف دوباره بودجه برای فراخوانی‌های موفق قبلی شود.
8. تعداد کل درخواست‌ها باید از سقف تنظیم‌شده عبور نکند.

همچنین مراقب باش Fallback باعث دور زدن محدودیت کلی Job نشود.

اگر بودجه کلی تمام شده، دیگر هیچ منبعی نباید درخواست جدیدی ارسال کند.

# بخش هشتم: Deduplication و جلوگیری از داده‌های تکراری

این قسمت از مهم‌ترین بخش‌های پروژه است.

هدف این است که یک کسب‌وکار، حتی اگر از چند MCP و چندین بار پیدا شود، فقط یک Lead داشته باشد.

## 8.1. شناسه‌های پایدار

برای تطبیق، اولویت استفاده از این موارد باشد:

1. National ID یا شناسه ملی شرکت
2. شناسه پایدار کسب‌وکار در همان Source
3. شماره تلفن عمومی نرمال‌شده
4. دامنه وب‌سایت
5. نام + نشانی + شهر
6. نام + تلفن
7. نام + دامنه

شناسه هر Source باید مستقل نگهداری شود.

شناسه یک فروشگاه در ترب نباید با شناسه همان فروشگاه در ایمالز یکسان فرض شود.

## 8.2. نرمال‌سازی

موارد زیر را پوشش بده:

- حروف فارسی و عربی
- ارقام فارسی و انگلیسی
- نیم‌فاصله
- فاصله‌های اضافی
- نشانه‌گذاری
- شماره تلفن با پیش‌شماره‌های مختلف
- دامنه با www و بدون www
- URLهای دارای مسیرهای متفاوت
- نام‌های دارای پسوندهای حقوقی مانند سهامی خاص و مسئولیت محدود
- نام‌های تجاری دارای اختلاف جزئی نگارشی

## 8.3. ادغام محافظه‌کارانه

هر شباهتی به معنی یکسان بودن کسب‌وکار نیست.

مثلاً دو شعبه یک فروشگاه ممکن است:

- نام یکسان
- تلفن یکسان
- دامنه یکسان

داشته باشند اما نشانی و مختصات متفاوتی داشته باشند.

این دو نباید بدون بررسی به یک رکورد تبدیل شوند.

قواعد ادغام باید بین موارد زیر تفاوت بگذارند:

- یک کسب‌وکار با چند منبع
- شعب مختلف یک کسب‌وکار
- شرکت مادر و زیرمجموعه
- دو کسب‌وکار با نام مشابه
- فروشنده یکسان در چند بازارگاه

## 8.4. Deduplication در زمان ذخیره

قبل از ایجاد Lead جدید:

- رکوردهای موجود در همان Job بررسی شوند.
- رکوردهای تکراری در سطح منبع بررسی شوند.
- اگر رکورد موجود بود، اطلاعات جدید به همان Lead اضافه شود.
- Source جدید به `source_names` اضافه شود.
- شناسه جدید در `source_record_ids` ثبت شود.
- Evidence جدید ذخیره شود.
- اطلاعات قبلی بدون دلیل بازنویسی نشوند.
- داده‌های متعارض علامت‌گذاری شوند.

از Transaction و در صورت نیاز قفل‌گذاری دیتابیس استفاده کن تا دو Worker هم‌زمان Lead تکراری نسازند.

## 8.5. Idempotency

این موارد باید تضمین شوند:

- اجرای مجدد یک Task
- Retry شدن Task پس از قطع Worker
- اجرای دوباره یک Adapter
- تکرار پاسخ MCP
- دریافت یک کسب‌وکار از چند Source
- ادامه Job پس از cooldown

هیچ‌کدام نباید Lead یا Evidence تکراری غیرضروری ایجاد کنند.

برای Evidence نیز یک کلید یکتای مناسب طراحی کن.

# بخش دهم: اصلاح وضعیت نهایی Job و تجربه کاربری

این بخش بسیار مهم است.

کاربر نباید برای محدودیت عادی سرویس‌های خارجی احساس کند برنامه باگ خورده است.

## 10.1. تفکیک وضعیت فنی و وضعیت کاربر

وضعیت داخلی منابع را از وضعیت نهایی Job جدا کن.

وضعیت‌های داخلی می‌توانند شامل این موارد باشند:

- COMPLETED
- PARTIAL
- SKIPPED
- RATE_LIMITED
- BUDGET_EXHAUSTED
- LONG_COOLDOWN
- FAILED

اما وضعیت نهایی Job باید بر اساس نتیجه واقعی کل عملیات تعیین شود.

## 10.2. قوانین وضعیت نهایی

### حالت اول: همه منابع موفق

وضعیت:

`COMPLETED`

نمایش:

«جست‌وجو با موفقیت تکمیل شد.»

### حالت دوم: یک منبع Rate Limit شده اما Fallback موفق بوده است

وضعیت:

`COMPLETED`

نمایش:

«جست‌وجو با موفقیت تکمیل شد.»

محدودیت منبع اصلی نباید به‌عنوان خطا به کاربر نمایش داده شود.

### حالت سوم: بعضی منابع به سقف fair-share رسیده‌اند

وضعیت:

`COMPLETED`

نمایش:

«جست‌وجو تکمیل شد.»

اطلاعات سهمیه در گزارش فنی یا بخش جزئیات منابع باقی بماند.

### حالت چهارم: یک منبع محدود شده و منبع جایگزین مناسبی وجود ندارد

اگر منابع دیگر کار را با موفقیت انجام داده‌اند:

وضعیت کلی:

`COMPLETED`

در کنار آن، یک پیام اطلاع‌رسانی خنثی نمایش بده:

«برخی منابع در این نوبت محدودیت دسترسی داشتند؛ نتایج منابع در دسترس جمع‌آوری شده‌اند.»

نباید عبارت «تکمیل با خطا» صرفاً به دلیل Rate Limit نمایش داده شود.

### حالت پنجم: خطای واقعی داخلی یا خطای غیرقابل بازیابی

در این وضعیت، بسته به نتایج موجود، وضعیت PARTIAL یا FAILED حفظ شود.

نباید خطاهای واقعی برنامه را پنهان کنی.

## 10.3. طراحی UI

در صفحه Job:

- وضعیت موفقیت باید واضح باشد.
- محدودیت منابع با رنگ هشدار قرمز نمایش داده نشود، مگر واقعاً خطای جدی باشد.
- برای محدودیت عادی از پیام اطلاع‌رسانی خنثی استفاده کن.
- تعداد کسب‌وکارهای یکتا نمایش داده شود.
- تعداد منابع موفق نمایش داده شود.
- تعداد منابعی که محدودیت داشته‌اند نمایش داده شود.
- وضعیت Fallback قابل مشاهده باشد.
- جزئیات فنی فقط در بخش جزئیات منابع یا Log مدیریتی نمایش داده شود.

نمونه پیام مناسب:

«جست‌وجو تکمیل شد. اطلاعات از منابع در دسترس جمع‌آوری شده‌اند.»

نمونه پیام نامناسب:

«تکمیل با خطا»

یا

«منبع X دچار خطا شد و عملیات ناموفق بود»

وقتی که در واقع منابع دیگر کار را به‌درستی انجام داده‌اند.

**مهم:** نمایش موفقیت به معنی ادعای پوشش کامل بازار نیست. اگر بعضی منابع در دسترس نبوده‌اند، محدودیت پوشش باید با زبان خنثی و شفاف بیان شود.

# بخش یازدهم: مدیریت Celery و ادامه Job

سیستم باید در برابر قطع Worker و اجرای مجدد مقاوم باشد.

موارد زیر را پیاده‌سازی یا اصلاح کن:

1. هر SourceExecution مستقل و قابل بازیابی باشد.

3. نتایج موفق بلافاصله ذخیره شوند.
4. Job پس از Restart Worker بتواند ادامه پیدا کند.
5. عملیات موفق قبلی دوباره اجرا نشوند.
6. Retryها دارای سقف باشند.
7. Cooldownهای طولانی با Celery countdown مدیریت شوند.
8. لغو Job توسط کاربر همچنان درست کار کند.
9. اجرای هم‌زمان دو Task برای یک Job باعث پردازش تکراری نشود.
10. task time limitها رعایت شوند.
11. هیچ Sleep طولانی و نامحدودی داخل Worker انجام نشود.

در صورت نیاز، یک مدل یا فیلد جدید برای نگهداری state و progress اضافه کن؛ اما ابتدا قابلیت‌های موجود را بررسی کن.

```env
SOURCE_FALLBACK_MAX_DEPTH=4

```

این نام‌ها پیشنهاد هستند. اگر تنظیمات مشابه از قبل وجود دارند، همان‌ها را توسعه بده و متغیر تکراری ایجاد نکن.

- مقدارهای پیش‌فرض را امن و منطقی انتخاب کن.
- مستندات تمام تنظیمات را در README بنویس.

# دستور نهایی

این پروژه باید به یک سیستم واقعی کشف کسب‌وکار تبدیل شود، نه مجموعه‌ای از MCPهای جداگانه که فقط به هم متصل شده‌اند.

تمرکز اصلی:

**Maximum Relevant Business Discovery + Reliable Fallback + Strong Deduplication + Resilient Execution**

تا جای ممکن اطلاعات کسب‌وکارها را از منابع مستقل و معتبر جمع‌آوری کن، اما هیچ‌وقت یک کسب‌وکار را چند بار ثبت نکن و برای محدودیت عادی یک سرویس، کل عملیات را ناموفق اعلام نکن.

تغییرات را واقعاً پیاده‌سازی کن؛ فقط به ارائه پیشنهاد یا نوشتن TODO اکتفا نکن.

هیچ‌گاه موفقیت تست یا اتصال زنده را بدون اجرای واقعی آن ادعا نکن.
