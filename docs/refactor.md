# دستور کامل ریفکتور پروژه `info_extractor`

می‌خواهم پروژهٔ موجود `info_extractor` را به‌صورت کامل و اصولی Refactor کنی. هدف، ساخت یک سیستم جست‌وجو و استخراج شماره موبایل کسب‌وکارهای ایرانی است.

Repository:
https://github.com/ARVIN-B/info_extractor

یک پروژهٔ مرتبط دیگر نیز وجود دارد که مسیرهای واقعی استخراج شماره تماس از منابع را بررسی کرده‌ایم:

https://github.com/ARVIN-B/develop_info_extractor

در صورت دسترسی، مستندات و نمونه‌خروجی‌های این مخزن را نیز بررسی کن. اطلاعات تأییدشدهٔ مسیرهای استخراج در ادامه آورده شده است.

**مهم:** قبل از هر تغییری، ساختار واقعی پروژه، مدل‌ها، سرویس‌ها، Adapterها، Taskهای Celery، تنظیمات، UI، تست‌ها و مستندات را بررسی کن. معماری و قابلیت‌های سالم فعلی را حفظ کن و تغییرات را روی همان پروژه اعمال کن. از ساخت پروژهٔ موازی یا بازنویسی بی‌دلیل بخش‌های سالم خودداری کن.

## ۱. هدف نهایی پروژه

کاربر در رابط کاربری پروژه یک عبارت جست‌وجو وارد می‌کند؛ مثلاً:

- رستوران
- فروشگاه موبایل
- کلینیک دندان‌پزشکی
- شرکت برنامه‌نویسی
- تعمیرگاه خودرو

سپس سیستم از چهار مسیر زیر به‌صورت هم‌زمان اطلاعات جمع‌آوری می‌کند:

1. Neshan MCP
2. Balad MCP
3. Emalls MCP
4. جست‌وجوی وب و استخراج اطلاعات از وب‌سایت‌ها

هدف، پیدا کردن تعداد مشخصی **شماره موبایل معتبر ایرانی و غیرتکراری** است.

کاربر باید هنگام ثبت هر جست‌وجو تعداد شماره موبایل موردنیازش را مشخص کند. سیستم باید تلاش کند به آن تعداد برسد.

مثلاً اگر کاربر عبارت «رستوران تهران» را جست‌وجو کند و تعداد ۱۰۰۰ شماره بخواهد، هر چهار مسیر باید به‌صورت موازی شروع به جست‌وجو کنند و تا رسیدن به ۱۰۰۰ شماره یکتا یا اتمام ظرفیت منابع، کار را ادامه دهند.

هیچ تضمینی دربارهٔ رسیدن به تعداد درخواستی وجود ندارد؛ نتیجه باید بر اساس دادهٔ واقعی منابع باشد.

## ۲. منابع مجاز

فقط همین سه منبع MCP باید در پروژه باقی بمانند:

- Neshan
- Balad
- Emalls

تمام منابع دیگر باید از چرخهٔ اجرای پروژه حذف شوند.

این حذف باید کامل باشد، نه صرفاً غیرفعال‌کردن در UI.

موارد زیر را بررسی و اصلاح کن:

- Source Adapterها
- Source Registry
- MCP Client Configuration
- تنظیمات منابع فعال
- وابستگی‌های Python
- فایل‌های requirements
- تنظیمات محیطی
- کدهای مربوط به منابع حذف‌شده
- مستندات
- تست‌ها
- بخش‌های رابط کاربری که منابع را نمایش می‌دهند

هیچ وابستگی یا فراخوانی غیرضروری به منابع حذف‌شده باقی نماند.

از طرف دیگر، ساختار Adapter-based فعلی را حفظ کن تا اضافه‌کردن منابع جدید در آینده آسان باشد.

## ۳. پیاده‌سازی دقیق استخراج شماره از MCPها

نکتهٔ بسیار مهم: در بررسی‌های قبلی، مسیرهای واقعی دریافت شماره تلفن در پاسخ MCPها مشخص شده‌اند. به‌جای اتکا به حدس یا استخراج عمومی، دقیقاً این مسیرها را پیاده‌سازی کن.

### Neshan

دو مسیر واقعی برای دریافت شماره تلفن:

**مسیر اول:**

`ns_search`

فیلد:

`results[].phone`

**مسیر دوم:**

`ns_place`

فیلد:

`phones[]`

رفتار مورد انتظار:

1. ابتدا جست‌وجو با `ns_search` انجام شود.
2. شماره‌های موجود در `results[].phone` استخراج شوند.
3. اگر شناسهٔ پایدار مکان موجود بود، در صورت نیاز برای دریافت جزئیات بیشتر `ns_place` اجرا شود.
4. شماره‌های موجود در `phones[]` نیز استخراج شوند.
5. شماره‌های تکراری حذف شوند.

اگر ابزار جزئیات به شناسهٔ مکان نیاز دارد، فقط از شناسهٔ واقعی خروجی استفاده کن.

### Balad

چهار مسیر واقعی:

**مسیر اول:**

`bl_search`

فیلد:

`results[].phone`

**مسیر دوم:**

`bl_nearby`

فیلد:

`places[].phone`

**مسیر سوم:**

`bl_nearest_by_drive`

فیلد:

`places[].phone`

**مسیر چهارم:**

`bl_along_route`

فیلد:

`places[].phone`

نکات مهم:

- ابزار `bl_nearby` پارامتر `with_phone` نیز دارد.
- اگر این پارامتر در Schema واقعی ابزار وجود دارد، هنگام جست‌وجو آن را فعال کن.
- اگر ابزارهای دیگر نیز پارامتر یا فیلتر مشابهی برای وجود شماره تلفن دارند، از آن استفاده کن.
- Schema واقعی هر ابزار را در زمان اتصال به MCP بررسی کن و آرگومان‌های نامعتبر ارسال نکن.
- برای جست‌وجوی معمول کسب‌وکار، از ابزارهای مناسب و قابل استفاده با اطلاعات جغرافیایی موجود در پروژه استفاده کن.
- ابزارهای مسیرمحور را فقط زمانی فراخوانی کن که پارامترهای لازم و مسیر معتبر در اختیار سیستم باشد؛ برای آن‌ها اطلاعات ساختگی تولید نکن.

### Emalls

مسیر واقعی:

`em_shop`

فیلد:

`phone`

در صورت نیاز، ابتدا فروشگاه‌ها را با ابزار جست‌وجوی موجود پیدا کن و سپس برای هر فروشگاه، جزئیات آن را با `em_shop` دریافت کن.

شمارهٔ موجود در پاسخ جزئیات فروشگاه را استخراج کن.

نام دقیق ابزارها و Schema را از MCP واقعی بخوان؛ به‌خصوص اگر نسخهٔ نصب‌شده با نمونه‌های قبلی تفاوت دارد.

### شرط مهم برای جست‌وجو

اگر ابزار یا منبعی پارامتری برای فیلترکردن نتایج دارای شماره تلفن دارد، حتماً از آن استفاده کن.

برای مثال، در Balad پارامتر `with_phone` را بررسی و فعال کن.

اگر چنین شرطی در Schema ابزار وجود ندارد، آرگومان جدید و غیرواقعی به آن اضافه نکن. در این حالت، خروجی را دریافت و در مرحلهٔ استخراج فیلتر کن.

## ۴. اضافه‌کردن جست‌وجوی وب و استخراج شماره تلفن

چهارمین مسیر، جست‌وجو در وب‌سایت‌های عمومی کسب‌وکارهای ایرانی است.

این مسیر باید مستقل از MCPها باشد و به‌صورت هم‌زمان با آن‌ها اجرا شود.

معماری پیشنهادی:

- SearXNG برای جست‌وجوی وب
- Firecrawl Self-hosted برای دریافت محتوا و Crawl صفحات
- Python برای استخراج و اعتبارسنجی شماره موبایل

تا حد امکان از سرویس‌های Self-hosted و متن‌باز استفاده کن.

### ۴.۱. SearXNG

یک Integration مستقل برای SearXNG بساز.

کاربر مثلاً عبارت «رستوران اصفهان» را وارد می‌کند.

سیستم باید با Queryهای مناسب، وب‌سایت‌ها و صفحات مرتبط را پیدا کند.

از چند Query هدفمند استفاده کن؛ برای مثال:

- رستوران اصفهان شماره تماس
- رستوران‌های اصفهان تماس با ما
- بهترین رستوران‌های اصفهان تلفن
- سایت رستوران اصفهان
- رستوران اصفهان موبایل

Queryها باید از عبارت اصلی کاربر و موقعیت جغرافیایی آن ساخته شوند. از تولید Queryهای بی‌ربط خودداری کن.

نتایج جست‌وجو باید شامل URLهای واقعی و قابل Crawl باشند.

### ۴.۲. Firecrawl Self-hosted

از Firecrawl برای دریافت محتوای وب‌سایت‌ها استفاده کن.

قابلیت‌های موردنیاز:

- Scrape
- Crawl
- دریافت محتوای صفحات
- دنبال‌کردن لینک‌های داخلی مرتبط
- استخراج متن صفحات
- دریافت صفحات تماس با ما، درباره ما و صفحات اطلاعات شعب

حداقل صفحات مهم برای بررسی:

- صفحهٔ اصلی
- تماس با ما
- درباره ما
- اطلاعات تماس
- شعب و نمایندگی‌ها

تعداد صفحات قابل Crawl برای هر دامنه باید قابل تنظیم باشد.

از Crawl بی‌نهایت جلوگیری کن.

برای جلوگیری از هدررفت منابع:

- دامنه‌های تکراری را حذف کن.
- URLهای تکراری را حذف کن.
- صفحات نامرتبط را Crawl نکن.
- صفحات تکراری و Queryهای تکراری را مجدداً پردازش نکن.
- برای هر دامنه سقف مشخصی از صفحات در نظر بگیر.

### ۴.۳. استخراج شماره موبایل از محتوا

در این قسمت به LLM نیازی نیست.

از Regex و اعتبارسنجی دقیق Python استفاده کن.

شماره‌های ایرانی ممکن است با شکل‌های مختلفی منتشر شوند:

- 09123456789
- ۰۹۱۲۳۴۵۶۷۸۹
- ٠٩١٢٣٤٥٦٧٨٩
- +989123456789
- 00989123456789
- 9123456789
- شماره‌هایی که با فاصله، خط تیره یا پرانتز نوشته شده‌اند

ابتدا ارقام فارسی و عربی را به انگلیسی تبدیل کن.

سپس جداکننده‌های مجاز را مدیریت کن و شماره را به قالب استاندارد تبدیل کن.

قالب نهایی همهٔ شماره‌ها باید این باشد:

`09XXXXXXXXX`

شرایط اعتبارسنجی:

- دقیقاً ۱۱ رقم
- شروع با `09`
- فقط موبایل معتبر ایران
- حذف شماره‌های ثابت
- حذف شماره‌های ناقص یا نامعتبر
- حذف مقادیر دارای ارقام اضافه یا فرمت مشکوک

Regex به‌تنهایی کافی نیست؛ بعد از استخراج، اعتبارسنجی و Normalization انجام بده.

شمارهٔ استخراج‌شده باید همراه با URL صفحهٔ منبع و دامنهٔ وب‌سایت در داده‌های داخلی ذخیره شود تا امکان بررسی و ردیابی وجود داشته باشد.

فقط اطلاعات تماس عمومی‌ای را پردازش کن که خود کسب‌وکار منتشر کرده است. شماره‌های خصوصی، اطلاعات شخصی نامرتبط و داده‌های غیرعمومی نباید استخراج شوند.

### ۴.۴. تنظیمات وب

تمام تنظیمات لازم را به `.env.example` اضافه کن.

حداقل تنظیمات:

- `SEARXNG_BASE_URL`
- `FIRECRAWL_BASE_URL`
- `WEB_SEARCH_ENABLED`
- `WEB_SEARCH_MAX_RESULTS`
- `WEB_SEARCH_MAX_DOMAINS`
- `WEB_CRAWL_MAX_PAGES_PER_DOMAIN`
- `WEB_CRAWL_MAX_DEPTH`
- `WEB_CRAWL_TIMEOUT`
- `WEB_SEARCH_TIMEOUT`
- `WEB_CRAWL_CONCURRENCY`

مقادیر پیش‌فرض منطقی و قابل تغییر باشند.

اگر SearXNG یا Firecrawl در دسترس نبود، مسیر وب باید خطای مستقل ثبت کند و اجرای سایر منابع را متوقف نکند.

اگر Docker Compose در پروژه وجود دارد، سرویس‌های SearXNG و Firecrawl را با ساختار فعلی هماهنگ کن. اگر وجود ندارد، در صورت نیاز یک Compose مناسب اضافه کن.

نکته: SearXNG خودش یک موتور جست‌وجوی مستقل با ایندکس کامل اینترنت نیست؛ از موتورهای جست‌وجوی پشتیبانی‌شده استفاده می‌کند. بنابراین محدودیت و دسترس‌پذیری نتایج Upstream را در نظر بگیر.

## ۵. دریافت تعداد شماره موردنیاز از کاربر

در هر جست‌وجوی جدید، از کاربر تعداد شماره موبایل موردنیاز را بپرس.

مثلاً:

- عبارت جست‌وجو: رستوران تهران
- تعداد شماره موردنیاز: ۱۰۰۰

این تعداد باید در مدل Job ذخیره شود.

یک محدودیت حداکثری قابل تنظیم نیز برای تعداد درخواستی تعریف کن تا درخواست‌های بسیار بزرگ باعث مصرف کنترل‌نشدهٔ منابع نشوند.

تعداد درخواستی باید معیار توقف جست‌وجو باشد.

## ۶. اجرای هم‌زمان چهار مسیر

این بخش از مهم‌ترین قسمت‌های پروژه است.

هر Job باید چهار مسیر مستقل داشته باشد:

1. Neshan
2. Balad
3. Emalls
4. Web Search + Crawl

هر چهار مسیر باید به‌صورت موازی اجرا شوند.

از Celery برای مدیریت اجرای مستقل و هم‌زمان Taskها استفاده کن.

ساختار پیشنهادی:

- یک Job اصلی برای جست‌وجو
- چهار Task مستقل برای چهار مسیر
- یک مکانیزم مشترک و امن برای ثبت نتایج
- یک مکانیزم مرکزی برای بررسی تعداد شماره‌های یکتا
- یک مکانیزم توقف یا خاتمهٔ Taskها پس از رسیدن به هدف

اگر معماری Celery فعلی قابلیت مناسبی برای این کار دارد، همان را توسعه بده.

### رفتار هنگام رسیدن به تعداد موردنظر

فرض کن کاربر ۱۰۰۰ شماره درخواست کرده است.

به محض اینکه مجموع شماره‌های یکتا به ۱۰۰۰ رسید:

- وضعیت Job به‌روزرسانی شود.
- به Taskهای فعال اعلام شود که جست‌وجو را متوقف کنند.
- Taskها از شروع درخواست‌های جدید غیرضروری خودداری کنند.
- نتایج قبلی حفظ شوند.
- اجرای Job به‌درستی خاتمه پیدا کند.

توجه: Taskهایی که در حال اجرای یک درخواست خارجی هستند ممکن است فوراً قابل لغو نباشند. در این شرایط پس از پایان درخواست جاری، از ادامهٔ کار جلوگیری کن.

### اگر به تعداد موردنظر نرسیدیم

اگر همهٔ منابع تمام شدند یا محدودیت‌های آن‌ها اجازهٔ ادامه نداد:

- Job با وضعیت مناسب پایان یابد.
- تعداد واقعی شماره‌های یکتا نمایش داده شود.
- تعداد موردنیاز و تعداد به‌دست‌آمده مشخص باشد.
- دلیل نرسیدن به هدف در گزارش Job ثبت شود.

هیچ‌وقت تعداد یا شمارهٔ ساختگی تولید نکن.

## ۷. حذف شماره‌های تکراری

مهم‌ترین معیار Deduplication باید خود شماره تلفن استانداردشده باشد.

مثلاً ممکن است یک شماره در هر سه منبع MCP و همچنین در وب‌سایت یک کسب‌وکار پیدا شود.

این شماره باید فقط یک بار در خروجی نهایی نمایش داده شود.

قبل از Deduplication:

1. ارقام را یکسان‌سازی کن.
2. شماره را به فرمت استاندارد `09XXXXXXXXX` تبدیل کن.
3. اعتبار شماره را بررسی کن.

سپس شمارهٔ استاندارد را به‌عنوان کلید یکتایی در نظر بگیر.

Deduplication باید در سطح کل Job و بین تمام چهار مسیر انجام شود؛ نه فقط در داخل هر منبع.

در دیتابیس نیز از Constraint مناسب برای جلوگیری از ثبت هم‌زمان شمارهٔ تکراری استفاده کن.

در صورت پیدا شدن یک شماره از چند منبع:

- یک رکورد نهایی برای شماره داشته باش.
- منبع اولیه را حفظ کن.
- منابع دیگری که همان شماره را گزارش کرده‌اند، در صورت نیاز به‌عنوان Evidence داخلی ثبت کن.
- رکورد تکراری جدید در خروجی ایجاد نکن.

از Race Condition در زمان ثبت هم‌زمان نتایج جلوگیری کن.

## ۸. ساختار اطلاعات خروجی

من در خروجی نهایی فقط این اطلاعات را لازم دارم:

| فیلد | الزامی |
|---|---|
| شماره موبایل | بله |
| نام منبع | بله |
| آدرس کسب‌وکار | خیر، در صورت وجود |

مثال:

| شماره موبایل | منبع | آدرس |
|---|---|---|
| 09123456789 | Neshan | تهران، خیابان ولیعصر |
| 09351234567 | Balad | اصفهان، خیابان چهارباغ |
| 09121234567 | Emalls | — |
| 09911234567 | Web | تهران، خیابان شریعتی |

نام منبع در خروجی باید یکی از این موارد باشد:

- Neshan
- Balad
- Emalls
- Web

نام کسب‌وکار، ایمیل، شبکه اجتماعی، شماره ثابت، شناسه ثبت، توضیحات و اطلاعات اضافی را در خروجی نهایی نمایش نده.

اگر آدرس در دسترس نبود، مقدار آن خالی باشد.

با این حال، اطلاعات فنی لازم برای Debug، ثبت Evidence، URL منبع وب و گزارش عملکرد را در دیتابیس داخلی حفظ کن.

خروجی JSON و Excel موجود پروژه را با همین ساختار جدید سازگار کن.

## ۹. رابط کاربری

رابط فارسی و RTL فعلی پروژه را حفظ کن.

در فرم جست‌وجو:

- عبارت جست‌وجو
- تعداد شماره موبایل موردنیاز

از کاربر دریافت شود.

در صفحهٔ وضعیت Job، موارد زیر نمایش داده شوند:

- تعداد شماره‌های یکتای پیدا شده
- تعداد درخواستی
- درصد پیشرفت بر اساس تعداد هدف
- وضعیت کلی Job
- وضعیت هر چهار منبع به‌صورت مستقل
- تعداد شماره‌های استخراج‌شده از هر منبع
- تعداد شماره‌های تکراری حذف‌شده
- تعداد خطاها و محدودیت‌های منابع

وقتی تعداد موردنظر تکمیل شد، وضعیت تکمیل نمایش داده شود.

اگر تعداد کامل نشد، تعداد واقعی و علت احتمالی آن نمایش داده شود.

در صفحهٔ نتایج فقط سه فیلد خروجی موردنظر کاربر را نشان بده:

- شماره موبایل
- منبع
- آدرس (در صورت وجود)

فیلتر، صفحه‌بندی و Export فعلی را نیز با ساختار جدید سازگار کن.

## ۱۰. مدیریت خطا و محدودیت منابع

هر منبع باید مستقل از بقیه باشد.

اگر Neshan خطا داد، Balad و Emalls و Web باید به کار خود ادامه دهند.

موارد زیر را مدیریت کن:

- Timeout
- HTTP 429
- Rate Limit
- قطع ارتباط MCP
- خطای Schema
- پاسخ خالی
- پاسخ نامعتبر
- خطای Crawl
- دامنهٔ غیرقابل دسترس
- پاسخ تکراری
- خطای دیتابیس

Retry باید محدود، کنترل‌شده و متناسب با نوع خطا باشد.

در مواجهه با 429، از Retry بی‌وقفه، IP Rotation یا تلاش برای دور زدن محدودیت سرویس استفاده نکن. Cooldown و محدودیت نرخ درخواست را رعایت کن.

محدودیت‌های هر منبع باید از تنظیمات قابل کنترل باشند.

## ۱۴. نکات مهم و غیرقابل چشم‌پوشی

- فقط شماره موبایل ایرانی معتبر در خروجی باشد.
- شماره ثابت نباید در خروجی نهایی نمایش داده شود.
- Deduplication فقط بر اساس شماره استانداردشده انجام شود.
- چهار مسیر باید مستقل و هم‌زمان اجرا شوند.
- تعداد هدف باید از کاربر دریافت شود.
- سیستم باید پس از رسیدن به تعداد هدف، اجرای غیرضروری را متوقف کند.
- تمام نتایج قبلی معتبر حفظ شوند.
- هیچ منبعی به‌جز Neshan، Balad، Emalls و Web فعال نباشد.
- هیچ API Key یا Secret واقعی را داخل کد یا مستندات قرار نده.
- اطلاعات تماس عمومی کسب‌وکارها را استخراج کن؛ عمومی‌بودن یک شماره به‌معنای رضایت صاحب آن برای دریافت پیامک تبلیغاتی نیست. قابلیت ارسال پیامک انبوه یا دورزدن محدودیت‌های ارتباطی در این پروژه پیاده‌سازی نکن و وضعیت مجوز/رضایت بازاریابی را از دسترسی عمومی شماره جدا نگه دار.
- محدودیت‌های واقعی هر منبع را در نظر بگیر؛ رسیدن به تعداد درخواستی را تضمین نکن.
- کدهای سالم موجود را بدون دلیل حذف یا بازنویسی نکن.
- هیچ‌وقت فقط برای پاس‌شدن تست، منطق غیرواقعی یا دادهٔ ساختگی اضافه نکن.

## ۱۵. ترتیب انجام کار

کار را به این ترتیب انجام بده:

**مرحله اول: بررسی کامل پروژه**

ساختار فعلی، مدل‌ها، Adapterها، Taskها، UI، تست‌ها و مستندات را بررسی کن. نقاطی را که باید تغییر کنند مشخص کن.

**مرحله دوم: طراحی معماری جدید**

ساختار نهایی را با حفظ معماری سالم موجود مشخص کن. مشخص کن هر یک از چهار مسیر چطور اجرا، نتیجه را ثبت و به مکانیزم مرکزی اعلام می‌کند.

**مرحله سوم: Refactor منابع MCP**

فقط Neshan، Balad و Emalls باقی بمانند و مسیرهای واقعی استخراج شماره پیاده‌سازی شوند.

**مرحله چهارم: پیاده‌سازی Web Search**

Integration مربوط به SearXNG و Firecrawl Self-hosted و استخراج شماره با Regex و اعتبارسنجی Python را پیاده‌سازی کن.

**مرحله پنجم: پیاده‌سازی اجرای موازی و Deduplication**

اجرای چهار مسیر، ثبت اتمیک شماره‌ها، مدیریت تعداد هدف و توقف کنترل‌شده را پیاده‌سازی کن.

**مرحله ششم: اصلاح UI و Export**

فرم دریافت تعداد، وضعیت Job، نمایش نتایج و خروجی‌ها را با نیاز جدید هماهنگ کن.

**مرحله هفتم: تست و مستندسازی**

تست‌ها را اجرا کن، خطاها را رفع کن و مستندات را به‌روزرسانی کن.

در پایان، یک گزارش دقیق ارائه بده که شامل این موارد باشد:

- فایل‌های اضافه‌شده
- فایل‌های تغییرکرده
- فایل‌ها و منابع حذف‌شده
- معماری نهایی
- نحوهٔ اجرای پروژه
- تنظیمات جدید محیطی
- تست‌های اجراشده و نتیجهٔ آن‌ها
- قابلیت‌هایی که کامل پیاده‌سازی شده‌اند
- مواردی که به دلیل محدودیت خارجی یا نبود دسترسی قابل تست نبوده‌اند

**هدف این است که پروژهٔ فعلی به یک سیستم کامل و قابل استفاده برای استخراج شماره موبایل کسب‌وکارهای ایرانی تبدیل شود، نه یک نمونهٔ اولیه یا MVP.**
